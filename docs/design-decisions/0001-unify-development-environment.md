# ADR 0001: 開発環境を共通の Compose 構成に統合する

## Compose 構成を一つにする

以前の七つの構成は重複が多く、更新をそろえる負担がありました。
どの対象ホストでもコンテナ内では Linux が動くため、Dockerfile と Compose 構成を
ルートに集約し、ホスト差はマウント、UID/GID、ファイル変更通知の扱いで調整します。
Livebook は Compose のプロファイルで任意に起動します。

`web` は PostgreSQL のヘルスチェックが成功してから起動します。
これは接続準備の確認であり、マイグレーションの代わりにはなりません。

## イメージと権限

ネイティブ依存関係を扱いやすい Debian ベースの Elixir `slim` イメージを使います。
amd64 と arm64 向けのイメージが公開されていますが、実機検証の範囲は
[検証記録](../worklog/20261119-development-smoke-test.md)に分けて記載します。

`bin/setup` がホストの UID/GID を取得し、Dockerfile が対応する非 root ユーザーを作ります。
指定された GID のグループがイメージ内に存在する場合は再利用します。
UID/GID を変えた場合はイメージを再ビルドします。

Livebook の attached runtime は同じ Elixir マイナーバージョンを要求するため、
web と Livebook のイメージは組み合わせて更新します。

## ソースとキャッシュ

ソースはバインドマウントで共有し、コード再読み込みを利用します。
依存関係とビルド成果物は `/cache/deps`、`/cache/_build` の名前付きボリュームに置き、
`MIX_DEPS_PATH` と `MIX_BUILD_ROOT` で指定します。
生成先とキャッシュを分けることで、アプリ生成前に `app/` が作られるのを防ぎます。

Phoenix のアセット処理はアプリからの相対パスも使うため、生成したアプリには
`deps/`、`_build/` からキャッシュへのリンクを作ります。

## Phoenix の標準構成を保つ

ディレクトリ名は常に `app` なので、生成時には `--app` と `--module` を明示します。
`--no-install` で生成した後、開発・テスト用の接続設定を追加して `mix setup` を実行します。
生成された設定全体は置き換えず、Compose のネットワークと HTTP 待受に必要な値だけを上書きします。

通常の esbuild/Tailwind はバイナリを自動取得するため、Node.js は既定では含めません。
npm を使うアプリでは必要に応じて追加します。

## ローカル開発での境界

- `.env` は Git 管理対象外とし、権限 0600 でランダムなローカル認証情報を保存します。
- PostgreSQL は `db:5432` でコンテナから接続し、ホストにはポートを公開しません。
- HTTP ポートはホストの `127.0.0.1` にのみ公開し、Livebook のトークン認証を有効にします。
- Erlang のノード間通信は Compose ネットワーク内で行い、`.env` のランダムな cookie を使います。
  Phoenix ノードには長いノード名 `phoenix@web.phoenix.test` とネットワーク別名で接続します。
- `docker compose config` は認証情報を展開して表示するため、出力を公開しないでください。

本番用イメージ、配備基盤、既存 PostgreSQL データの自動更新は対象外です。
